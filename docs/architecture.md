# Архитектура лаборатории

`anum_parser` строится как маленький статический стенд. Главная задача — делать различия видимыми и сравнивать конкурирующие алгоритмы на одинаковом входе.

## Слои

```text
исходные байты / поле ввода
        ↓
чтение формата
        ↓
последовательность символов
        ↓
лексический профиль / словарь
        ↓
абиты или ссылки на связи
        ↓
выбранный десериализатор
        ↓
каноническая асеть + трасса
        ↓
выбранный сериализатор / визуализация
```

## Базовая identity МТС

Для лаборатории после `anum_docs#343` действует аксиома:

```text
(A ⟼ B) = (C ⟼ D)
⇔
A = C ∧ B = D
```

Связь полностью определяется своими полюсами.

Следовательно, внутренний строитель асети работает как:

```text
ensureLink(start,end):
    если связь такой формы уже есть -> вернуть её
    иначе -> добавить её
```

Технический `id` нужен только для адресации записи в JSON и интерфейсе. Он не является дополнительным уровнем смыслового тождества.

Это важно отличать от сети дуплетов Теории связей, где существует отдельное множество ссылок и отображение ссылки в пару значений.

## Семь различаемых представлений

### 1. Последовательность символов

Физический/лексический уровень. Для `.anums` это Unicode-символы; для `.anum4` — четыре ASCII-знака.

### 2. Последовательность абитов

Результат явного профиля разрешения `[ ] 1 0`. Даже при физическом совпадении с исходными символами это отдельное представление.

### 3. Связь

Объект МТС, однозначно определяемый парой:

```text
start ⟼ end
```

Нельзя иметь две различные связи одной формы.

### 4. Последовательность ссылок на связи

Упорядоченный список позиций. Одна и та же связь может встречаться в списке несколько раз:

```text
[A, B, A, A]
```

Повтор позиции не создаёт новые экземпляры `A`.

### 5. Акорневая связь-последовательность

Носитель, построенный как левая цепочка от акорня:

```text
R ⟼ v1
(R ⟼ v1) ⟼ v2
...
```

Каждый шаг канонизируется по своим полюсам. Если такая связь уже существует, она переиспользуется.

### 6. Связь, играющая роль хранения ачисла

Экспериментальная роль связи формы:

```text
carrier ⟼ denotation
```

Если связь такой формы уже есть, роль хранения указывает на неё же. Роль не даёт связи новую identity.

### 7. Денотат

Результат конкретной стратегии десериализации. Он может совпасть с carrier или storage-link по форме, а может отличаться.

## Корневой базис четверичного профиля

Лаборатория содержит:

```text
R = R ⟼ R
O = O ⟼ R
C = R ⟼ C
L = O ⟼ C
U = C ⟼ O
```

и словарь:

```text
[ -> O
] -> C
1 -> L
0 -> U
```

Поэтому физическая последовательность:

```text
1101
```

разрешается как:

```text
[L, L, U, L]
```

а не как четыре новых экземпляра связей.

## Строковые символы

Строковый профиль пока экспериментален. Для замкнутой лабораторной модели Unicode-символ разрешается в детерминированную связь через его UTF-8-код, представленный последовательностью корневых `L/U`.

Важное свойство:

```text
одинаковый символ -> та же связь
разные позиции символа -> разные позиции последовательности
```

Например `aba` может дать:

```text
[A, B, A]
```

Это экспериментальный способ разрешения строкового словаря, не нормативное определение символов МТС.

## Реестр десериализаторов

Каждый алгоритм имеет:

```js
{
  id,
  title,
  status,
  inputKinds,
  deserialize(source, options)
}
```

Статус обязателен:

- `historical`;
- `experimental`;
- `accepted`;
- `rejected`.

Интерфейс не предполагает, что выбранный первым алгоритм является истинным.

## Первые варианты десериализации

### `string-flat-v0`

Строковые Unicode-символы разрешаются словарным экспериментом в канонические связи. Денотат — левая свёртка. Отдельно строится акорневой carrier.

### `abit-flat-v0`

Все `[ ] 1 0` рассматриваются как четыре корневые связи и сворачиваются слева. Никакой стековой семантики.

Этот вариант нужен как контрольный контрпример.

### `stack-group-value-v0`

- `[` — открыть контекст;
- новый контекст начинается от `R`;
- `1/0` — значения текущего контекста;
- `]` — закрыть контекст и передать его результат родителю как одно значение;
- пустая группа возвращает `R`;
- левая свёртка непустой группы начинается с первого значения.

Это экспериментальная стратегия закрытия.

### `stack-root-wrap-v0`

Как предыдущий вариант, но при закрытии непустого контекста внутренний результат проходит через связь:

```text
R ⟼ inner
```

По аксиоме identity эта операция также канонична: если `R⟼inner` уже существует, повторный шаг возвращает ту же связь.

## Стековая машина и #17

Десериализатор должен иметь интерактивный режим пошагового исполнения. Для каждого шага интерфейс должен уметь показать:

- текущую физическую позицию;
- текущий символ;
- разрешённый абит/связь;
- текущий контекст;
- стек сохранённых контекстов;
- указатель вершины стека;
- текущую связь;
- какие связи **добавились** на этом шаге;
- какие существующие связи были переиспользованы.

Это особенно важно после identity-by-poles: повторная операция `A⟼B` может ничего не добавлять в асеть, потому что связь уже существует.

## Трасса

Каждый десериализатор возвращает пошаговую трассу:

```js
{
  step,
  token,
  operation,
  depth,
  current,
  values,
  producedLinks,
  note
}
```

Трасса — отладочное свидетельство алгоритма. Она не является новой онтологией МТС.

В следующем шаге #17 трасса будет расширена снимком стека и возможностью двигаться вперёд/назад по шагам.

## Реестр сериализаторов

Сериализатор выбирается отдельно от входного формата и десериализатора. Наличие асети само по себе не означает, что из неё можно однозначно получить четверичное или строковое ачисло.

Первый реестр содержит:

- `aset-json-v0` — сохранить `.aset.json`;
- `source-replay-v0` — вернуть исходные `.anum4`/`.anums`, только если `provenance.source` это доказывает;
- `source-envelope-v0` — сохранить тот же физический источник в `.anum.json`.

Отдельно `storage-link-v0` остаётся экспериментальной топологической ролью, а не отдельным типом связи.

## Корпус экспериментов

`examples/cases.json` — единый набор физических входов. Node-тесты исполняют каждый случай отдельно.

Кроме примеров скобочной семантики обязательны фундаментальные проверки:

```text
ensureLink(A,B) == ensureLink(A,B)
```

и отрицательный импорт:

```text
{id:X,start:A,end:B}
{id:Y,start:A,end:B}
```

который обязан быть отвергнут как `duplicate-link-form`.

Для акорня:

```text
R ⟼ R = R
```

поэтому, например, результат `[][]` в стратегии «группа возвращает значение» схлопывается обратно в `R`.

## Визуализация

Cytoscape.js представляет **связи как узлы интерфейса**. Для каждой связи `L` показываются два направленных отношения:

```text
L --начало--> start(L)
L --конец----> end(L)
```

Интерфейс поддерживает CoSE и альтернативные раскладки, pan, zoom и ручное перемещение связей.

Визуализация не должна допускать два узла только потому, что файл содержит два технических `id` одной формы: такой `.aset.json` невалиден ещё до визуализации.

## Граница с `anum_docs`

Эксперимент считается кандидатом на перенос только если:

1. алгоритм имеет устойчивый `id`;
2. корпус зелёный;
3. контрпримеры перечислены;
4. известны свойства восстановления исходника, топологии и семантики;
5. модель не противоречит базовой identity связи #343;
6. принято отдельное решение в `anum_docs`.

До этого всё остаётся локальной моделью `anum_parser`.
