# Форматы файлов лаборатории

Версия документа: `0.2-experimental`.

Форматы ниже предназначены для экспериментов `anum_parser`. Они не объявляют конкретный сериализатор или стратегию закрытия скобок нормативной для МТС.

## 1. Raw четверичное ачисло — `.anum4`

Минимальная физическая запись последовательности абитов без метаданных.

### Профиль `mts-abit-v1`

Допустимы ровно четыре ASCII-байта:

```text
[ ] 1 0
```

Правила:

- кодировка физически ASCII и тем самым валидный UTF-8;
- BOM запрещён;
- пробелы, CR/LF, комментарии и прочие символы не игнорируются молча;
- `∞` не хранится как пятый символ;
- пустой файл разрешён как пустая физическая последовательность;
- смысл пустой последовательности определяется выбранным десериализатором;
- файл хранит **последовательность символов**; превращение этих символов в **последовательность абитов** является отдельным шагом профиля.

Примеры:

```text
[]
[10]
[[10]]10
10[10]
```

## 2. Raw строковое ачисло — `.anums`

Человекочитаемая последовательность Unicode-символов.

Правила:

- кодировка UTF-8;
- BOM запрещён;
- Unicode normalization (`NFC/NFD/NFKC/NFKD`) не выполняется автоматически;
- порядок Unicode scalar values сохраняется;
- пустая строка разрешена;
- символы строки не считаются абитами автоматически;
- `a`, `window`, `🙂`, `[` — прежде всего символы исходной строки;
- перевод символов в связи требует явного словаря/профиля.

Примеры:

```text
abc
window(position)(x)(10)(int)
boolean(true)
🙂
```

## 3. Самодокументируемый artifact — `.anum.json`

Используется интерфейсом, тестами и обменом экспериментами. Raw-форматы он не заменяет.

Минимальный пример:

```json
{
  "format": "mts-anum",
  "version": "0.1",
  "kind": "quaternary",
  "profile": "mts-abit-v1",
  "data": "[10]",
  "provenance": {
    "status": "experimental"
  }
}
```

Для строки:

```json
{
  "format": "mts-anum",
  "version": "0.1",
  "kind": "string",
  "encoding": "utf-8",
  "data": "abc"
}
```

Поле `profile` описывает физический/лексический профиль. Алгоритм десериализации выбирается отдельно.

## 4. Наглядная асеть — `.aset.json`

### Цель

Сохранить топологию связей и одновременно показать служебные представления, не смешивая их с самой асетью.

### Базовый инвариант МТС

```text
(A ⟼ B) = (C ⟼ D)
⇔
A = C ∧ B = D
```

Поэтому `.aset.json` версии `0.2` использует:

```json
"identity": "by-poles"
```

и **запрещает** две разные записи связей с одной парой `(start,end)`.

`id` является техническим адресом записи внутри файла. Он нужен для ссылок и удобства визуализации, но не создаёт дополнительную семантическую identity связи.

### Базовая структура

```json
{
  "format": "mts-aset",
  "version": "0.2",
  "identity": "by-poles",
  "root": "R",
  "links": [
    {"id":"R", "start":"R", "end":"R"},
    {"id":"O", "start":"O", "end":"R"},
    {"id":"C", "start":"R", "end":"C"},
    {"id":"L", "start":"O", "end":"C"},
    {"id":"U", "start":"C", "end":"O"}
  ],
  "labels": {
    "R": "∞",
    "O": "[",
    "C": "]",
    "L": "1",
    "U": "0"
  },
  "symbolSequences": [],
  "abitSequences": [],
  "linkSequences": [],
  "rootChains": [],
  "storedAnums": [],
  "provenance": {}
}
```

## 5. Корневой базис

Лабораторная асеть `0.2` содержит пять канонических связей:

```text
R = R ⟼ R
O = O ⟼ R
C = R ⟼ C
L = O ⟼ C
U = C ⟼ O
```

Корневой словарь четверичных абитов:

```text
[ -> O
] -> C
1 -> L
0 -> U
```

Одинаковый абит, встреченный несколько раз во входе, несколько раз появляется **в последовательности ссылок**, но не создаёт несколько связей одной формы.

Например:

```json
{
  "symbols": ["1", "1", "0"],
  "refs": ["L", "L", "U"]
}
```

## 6. `links`: канонические связи

Каждая запись имеет форму:

```json
{"id":"L42","start":"L10","end":"L11"}
```

Для каждой пары `(start,end)` допустима не более чем одна запись.

Недопустимо:

```json
{"id":"L1","start":"A","end":"B"}
{"id":"L2","start":"A","end":"B"}
```

Потому что по МТС это одна и та же связь. Импортёр обязан выдать `duplicate-link-form`, а не сохранять два экземпляра.

`labels` и `tags` являются метаданными лабораторного файла и не изменяют топологию или identity связи.

## 7. `symbolSequences`

Исходная последовательность символов:

```json
{
  "id": "source:0",
  "kind": "utf8-symbols",
  "items": ["a", "b", "a"],
  "text": "aba"
}
```

Это **не последовательность связей**.

Если выбранный словарь разрешает одинаковый символ в одну связь `A`, последующая последовательность ссылок может быть:

```text
[A, B, A]
```

Повтор позиции не означает копирование связи `A`.

## 8. `abitSequences`

После явного разрешения корневым словарём:

```json
{
  "id": "abits:0",
  "profile": "mts-abit-v1",
  "symbols": ["[", "1", "0", "]"],
  "refs": ["O", "L", "U", "C"]
}
```

`symbols` — физические знаки, `refs` — связи, выбранные словарём для каждой позиции.

## 9. `linkSequences`

Упорядоченный список ссылок на связи:

```json
{
  "id": "links:0",
  "items": ["A", "B", "A"]
}
```

Последовательность допускает повтор одной ссылки. Список сам по себе **не материализует** `(A⟼B)⟼A`; он только фиксирует порядок.

## 10. `rootChains`

Связь-последовательность, исходящая из акорня:

```json
{
  "id": "carrier:abc",
  "sourceSequence": "links:0",
  "items": ["A", "B", "C"],
  "head": "RC3"
}
```

Её структура:

```text
RC1 = R   ⟼ A
RC2 = RC1 ⟼ B
RC3 = RC2 ⟼ C
```

Если один из этих шагов уже существует в асети, он **переиспользуется**, а не создаётся повторно.

Особенно:

```text
R ⟼ R = R
```

поэтому добавление акорня к акорню не создаёт новой root-shaped связи.

## 11. `storedAnums`

Исторические схемы требуют различать:

- carrier ачисла;
- его денотат;
- роль связи, хранящей соответствие между ними.

```json
{
  "id": "stored:0",
  "storageLink": "S1",
  "carrier": "RC3",
  "denotation": "D2",
  "serializer": "storage-link-v0",
  "status": "experimental"
}
```

`storageLink` имеет форму:

```text
carrier ⟼ denotation
```

Но если связь такой формы уже существует по другой причине, роль хранения ссылается на **ту же связь**. Роль не создаёт второй экземпляр пары полюсов.

## 12. `provenance`

Рекомендуемые поля:

```json
{
  "source": {
    "kind": "quaternary",
    "profile": "mts-abit-v1",
    "raw": "[10]"
  },
  "deserializer": "stack-group-value-v0",
  "serializer": null,
  "status": "experimental",
  "traceVersion": "0.2"
}
```

История/трасса может различать несколько актов получения одной связи. Это различие актов не превращается в multiplicity самой связи.

## 13. Round-trip уровни

### `source-round-trip`

Можно без потерь восстановить те же raw bytes/source text.

### `topology-round-trip`

Можно восстановить каноническую сеть пар `(start,end)` и служебные ссылки файла. Технические `id` могут сохраняться для стабильности artifact, но семантическое тождество ими не определяется.

### `semantic-round-trip`

Serializer(deserializer(x)) даёт эквивалентный смысл по конкретной теории. Это самое сильное обещание и не предполагается автоматически.

## 14. Ошибки

Импортёр должен выдавать diagnostic, а не исправлять молча:

- `invalid-utf8`;
- `bom-not-allowed`;
- `invalid-abit-symbol`;
- `unknown-format-version`;
- `dangling-link-ref`;
- `duplicate-link-id`;
- `duplicate-link-form`;
- `missing-root`;
- `invalid-root-kernel`;
- `unsupported-round-trip`;
- `algorithm-undefined-transition`.

## 15. Расширение форматов

Новая версия меняет `version`, если меняется структура или фундаментальное обещание файла. Поэтому переход от occurrence-multiplicity `0.1` к identity-by-poles оформлен как `.aset.json` `0.2`.

Новый вариант смысла скобок не обязан менять формат: он получает новый `deserializer/serializer id`. Это позволяет одному `.anum4` сравниваться десятками алгоритмов без переписывания входного файла.
