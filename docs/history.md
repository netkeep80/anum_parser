# Историческая модель ачисел

Этот документ — рабочая выжимка исторических записей автора МТС для экспериментального репозитория. Он **не является нормативной спецификацией МТС**. Противоречащие друг другу варианты сохранены как варианты, а не склеены задним числом.

## Статусы

- `historical-observation` — явно присутствует в старых записях или схемах;
- `historical-hypothesis` — старое предлагаемое объяснение/алгоритм;
- `current-invariant` — различение, которое сохраняется в текущем экспериментальном цикле;
- `experiment-candidate` — вариант, который стоит проверять кодом;
- `superseded` — исторический вариант, который нельзя молча использовать как текущий канон.

## 1. Ачисло как последовательность и как адрес

`historical-observation`

В старых материалах ачисло одновременно описывалось как:

1. ассоциативное число / последовательность абитов;
2. сериализация структуры связей;
3. относительный адрес связи;
4. путь последовательного построения/нахождения связи.

На схеме «ачисла» прямо записано: **«АЧИСЛО есть относительный адрес связи»**.

`current-invariant`

Для лаборатории термин «ачисло» сам по себе недостаточен. Всегда указываем представление: источник, абиты, последовательность ссылок, carrier, денотат или роль хранения.

## 2. Неявный акорень

`historical-observation`

Во многих старых формулах последовательность символов строится от `∞`:

```text
"ab"  ->  (∞ -> a) -> b
"abc" -> ((∞ -> a) -> b) -> c
```

Акорень часто опускается в записи, потому что подразумевается как начало последовательности.

`current-invariant`

Акорень не смешивается с передаваемым символом. Raw-формат четверичного ачисла не требует пятого абита для `∞`.

## 3. Левоассоциативная последовательность связей

`historical-observation`

Старый архив многократно фиксирует левоассоциативность:

```text
abcd = ((a -> b) -> c) -> d
abv  = (a -> b) -> v
```

При этом полезно различать:

```text
carrier("abc") = ((∞ -> a) -> b) -> c
denotation(abc) = (a -> b) -> c
```

Они совпадают только тогда, когда совпадают их начала и концы по аксиоме тождества связи МТС.

## 4. Четверичные ачисла: исторические алфавиты

### 4.1. Ранний вариант `()+-`

`historical-observation`

В части старого архива используется ровно четыре знака:

```text
(  )  +  -
```

Встречается сопоставление открытия/закрытия и двух направлений связи вокруг акорня.

### 4.2. Поздний вариант `[]10`

`historical-observation`

В более поздних материалах четверичный алфавит записывается как:

```text
[  ]  1  0
```

Исторические обсуждения меняли ориентацию и смысл пар `[]`, `][`, поэтому лаборатория хранит идентификатор профиля алфавита.

`current-invariant`

Первый raw-формат лаборатории использует `[ ] 1 0`; конкретная семантика `OPEN/CLOSE` остаётся предметом эксперимента.

## 5. Скобки и вложенный контекст

`historical-observation`

Старые материалы трактовали скобки как:

- группировку;
- границы контекста сериализации;
- вход/выход из вложенного конструирования;
- способ описания ачисла, которое само является значением другого ачисла.

`experiment-candidate`

Актуальный путь — стековая машина: открытие контекста сохраняет внешнее состояние и начинает внутреннее от акорня. Правило закрытия сравнивается несколькими вариантами до отдельного принятия.

## 6. Строковые ачисла

`historical-observation`

В старых примерах присутствуют:

```text
window(position)(x)(10)(int)
window(position)(y)(20)(int)
boolean(true)
boolean(false)
null
```

На рукописной схеме слова изображены как акорневые цепочки букв, а повторяющиеся сущности связываются пометками `ref`.

`current-invariant`

Строковый символ не является абитом автоматически. Имя или символ должен разрешаться явным словарём/профилем в связь.

Повтор одного имени в последовательности не требует новой связи: разные позиции могут ссылаться на одну связь.

## 7. Последовательность символов != последовательность абитов

`current-invariant`

Лаборатория хранит раздельно:

```text
symbol-sequence
abit-sequence
```

Даже если физически строка состоит только из `[ ] 1 0`, переход от символов к абитам — отдельный шаг профиля.

## 8. Последовательность ссылок != связь-последовательность

`current-invariant`

Упорядоченный список:

```text
[a, b, a]
```

не является автоматически связью. Одна ссылка может повторяться сколько угодно раз.

Акорневая связь-последовательность — уже топология:

```text
c1 = ∞ -> a
c2 = c1 -> b
c3 = c2 -> a
```

Для каждой пары полюсов в МТС существует одна связь, поэтому уже имеющийся шаг переиспользуется.

## 9. Carrier != денотат != роль хранения

`historical-observation` + `current-invariant`

На исторической схеме «связь-ачисло» разведены сама связь `abc` и связь `[abc]`, кодирующая её ачисло.

Лаборатория различает:

```text
source      — физическая запись;
carrier     — связь-последовательность от ∞;
denotation  — связь, полученная выбранной десериализацией;
storageLink — связь формы carrier -> denotation, которой назначена роль хранения.
```

Эти роли могут указывать на одну и ту же связь, если совпадают полюса. Роль не создаёт второй экземпляр связи.

## 10. Тождество связи: исправление 2026-08-10

`current-invariant`

В ранней версии этой лаборатории была ошибочно перенесена в МТС модель сети дуплетов Теории связей, допускающая отдельный идентификатор ссылки поверх пары полюсов. Отсюда появилось неверное утверждение:

```text
L1 = a -> b
L2 = a -> b
L1 != L2
```

Для МТС это неверно.

Правильная аксиома:

```text
(A -> B) = (C -> D)
⇔
A = C и B = D
```

Следовательно:

```text
L1 = a -> b
L2 = a -> b
=> L1 = L2
```

Технические адреса записей памяти, события построения, позиции последовательности и история вычисления могут различаться, но они не создают две МТС-связи одной формы.

Это одно из важных отличий МТС от дуpletной модели ТС.

## 11. Инкрементальная и выборочная обработка

`historical-observation`

В обсуждении Anum Protocol (2024) были сформулированы требования:

- сериализация/десериализация инкрементальна;
- несколько ачисел могут загружаться в одну апамять и складываться;
- обработка может быть выборочной — вся асеть или выбранная часть;
- вход и выход прототипа могут быть файлами anum;
- отдельно нужен JSON;
- визуальная часть должна показывать модель асети;
- рассматривался web-доступ.

Эти требования прямо переходят в текущую лабораторию.

## 12. JSON и единое связевое хранилище

`historical-hypothesis`

В старых обсуждениях рассматривалась идея представлять все типы через anum и выполнять JSON-сериализацию поверх ассоциативной памяти.

`experiment-candidate`

Текущий `.aset.json` — наглядный interchange/debug format, а не часть онтологии. Версия `0.2` требует каноничность связей по `(start,end)`.

## 13. Что дают исторические схемы тестам

### `pic1`

- слова и типы представлены акорневыми цепочками символов;
- повторное использование идёт через `ref`;
- `window/position/x/y/int`, `boolean/true/false`, `null` полезны как corpus строковой сериализации.

### `ачисла`

- ачисло как относительный адрес;
- 0/1 и скобочные варианты;
- числовые разряды и буквенные последовательности;
- list-like связевые цепочки;
- различение направления/роли связи.

### `десериализация`

- связь как единственный базовый объект;
- мультиссылка означает несколько использований одной связи, а не несколько экземпляров одинаковой формы;
- старые формы `10(10)` и вложенные последовательности полезны как конкурирующие тесты.

### `связь-ачисло`

- связь, кодирующая ачисло `[abc]`;
- отдельно сама связь `abc`;
- источник различения carrier, denotation и storage-role.

## 14. Что сознательно не канонизируем

`superseded / unresolved`

Без отдельного experiment profile не принимаем как закон:

- конкретное старое соответствие `()+-` ролям;
- конкретное старое соответствие `[]` или `][` значениям;
- конкретный алгоритм `CLOSE`;
- запрет форм только по старым заметкам;
- скрытый стек языка реализации;
- отождествление исходного carrier с денотатом.

А вот **тождество связи по полюсам уже не является экспериментом**: лаборатория обязана соблюдать его как базовую аксиому МТС.
